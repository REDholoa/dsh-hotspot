# dsh-hotspot · 热点雷达

B站 / 抖音 网络热点与热梗聚合面板，作为 [DeepSeek Harness](https://github.com/deepseek-ai) 插件运行。
**每天 06:00 自动更新一次**，在 DSH 网页界面左侧边栏点一下图标就能看到一个独立面板，
五个页签：**概览 / 流传榜 / 热点榜 / 原始榜 / 统计**。

- **流传榜**：不是热度榜，而是按「被多少人反复用」排的**流传度榜**
  （只统计热搜词 / 热榜条目这类被复用的表达，**视频内容不参与**）；
- **热点榜**：按聚合后的综合热度排的话题榜（事件常占多个榜位，聚合后才有意义）；
- 数据来源：B站与抖音的**官方公开接口直连为主**，第三方聚合接口兜底；
- 每天 06:00（本地时间）自动抓一次，插件启动时若当天还没有数据会立刻补一次；
- 每天的快照落在磁盘上（默认保留 30 天），因此可以出「新上榜 / 掉榜 / 持续热梗 / 多日趋势」；
- 数据源全部挂掉时不会白屏：会展示上一次成功的结果并标注来源异常；
- 纯 JavaScript，**无构建步骤、无第三方依赖**，改完源文件即生效。

## 安装

手工装进某个 profile（本插件开发时走的就是这条路，已实测）：

```bash
cd ~/.dsh/profiles/<你的 profile>      # 通常是 default 或 desktop
pnpm add github:REDholoa/dsh-hotspot
```

然后把 `dsh-hotspot` 追加到该 `package.json` 的 `dsh.profile.bundles` 数组里：

```json
{ "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "...", "dsh-hotspot"] } } }
```

也可以用 DSH 的插件管理器（「设置 → 插件」）安装：它的安装规格会透传给 pnpm，
填下面这个即可（这条路径没有在本机实测过，若管理器不接受该规格，请用上面的手工方式）：

```
github:REDholoa/dsh-hotspot
```

装好之后**重启一次 DSH**（Host 半边需要重新加载；客户端半边会热重载），
左侧边栏就会出现「热点」图标。之后每天 06:00 会自动更新。

> 插件不含任何需要填写的 API Key 或账号配置：所有数据都来自公开只读接口。

## 数据来源与回退顺序

每个「数据槽」有一组按优先级排列的 provider，依次尝试，第一个成功且非空的结果胜出。
实际上线时的回退链：

| 槽位 | 优先级 | 接口 | 类型 |
|---|---|---|---|
| B站视频 | 1 | `api.bilibili.com/x/web-interface/ranking/v2` | 官方 |
| B站视频 | 2 | `v.api.aa1.cn/api/bilibili-rs` | 第三方 |
| B站热搜 | 1 | `api.bilibili.com/x/web-interface/search/square` | 官方 |
| B站热搜 | 2 | `app.bilibili.com/x/v2/search/trending/ranking` | 官方（App 端，与 PC 端不同源） |
| 抖音热榜 | 1 | `www.douyin.com/aweme/v1/web/hot/search/list/` | 官方 |
| 抖音热榜 | 2 | `60s.viki.moe/v2/douyin` | 第三方 |
| 抖音热榜 | 3 | `api.qqsuu.cn/api/dm-douyinhot` | 第三方 |

> 实测（2026-10）：抖音官方热榜接口**无需 Cookie / 无需签名**即可返回完整 `word_list`，
> B站的排行榜与热搜广场同样免鉴权。第三方接口只作为官方接口不可用时的兜底。

页面上会显示每个槽位**实际用的哪个 provider**，以及本轮的尝试记录；出错时不需要翻日志。

## 面板说明

### 概览
四张数字卡（梗条目 / 热点条目 / 热度合计 / 跨平台共现词数）、**梗榜 Top 8** 与 **热点榜 Top 8**
（都是聚合后的排行，可直接展开）、**跨平台共现词**（同一话题同时出现在 B站与抖音，通常意味着破圈）、
以及**今日新上榜**。

### 流传榜（梗榜）
**这不是热度榜，而是流传度榜** —— 排的是「哪个词被大量人反复用」，与热度值无关。

- **只统计短语**：B站热搜词 + 抖音热榜条目。**视频内容不参与**（视频是作品，不是被复用的表达）；
- 一行 = 一个**被反复复用的词**（如 `郑钦文`、`桂花香`、`S16`）；
- 行上显示：名次、词、细分标签、梗/热点标签、平台构成、`N 条 · 流传度 X`，
  下一行小字给出拆解：`N 条用到 · 出现 D 天 · 覆盖 P 个平台`；
- **点任意一行展开**，看到这个词被哪些条目用到（含平台、榜单类型、名次）；
- 顶部有**范围切换**：`全部 / 仅梗 / 仅热点`；下面还有**细分筛选条**。

### 热点榜
按**综合热度**排序的**话题**榜（事件常常同时占据多个榜位，聚合后才有意义）：

- 一行 = 一个**话题**，可能是多条条目聚合的结果；
- 行上显示：名次、话题名、细分标签、平台构成（B站 n / 抖音 n）、`条目数 · 综合热度`；
- **点任意一行展开**，看到这条热度由哪几条构成；
- 上方是**细分筛选条**：点某个细分只看该类话题，再点取消。

### 原始榜
不做任何聚合，按平台原样展示：B站热搜 / B站排行 / 抖音热榜 三选一。

### 统计
- **梗 / 热点构成**环形图；
- **流传榜 · 细分构成**与**热点 · 细分构成**；
- **来源构成**、**热度分档**、**B站分区分布**；
- **近 14 天条目数趋势**折线（梗 / 热点两条线，另附按来源拆分的一条）；
- **标题高频词**；
- **持续热梗**：同一关键词在近 14 天内出现在 ≥2 天的热搜榜上，天数越多越「梗」；
- **与上一份快照对比**：新上榜与掉榜。

## 算法口径（重要，避免过度声称）

### 梗 / 热点的划分
两组含义是「**娱乐 / 生活 / 流行文化**」对「**时事 / 事件 / 信息**」。判别顺序：

1. **B站视频优先用官方分区（tname）**。分区是平台自己打的标，比关键词可靠；
   用模式匹配（`TNAME_NEWS_RE` / `TNAME_MEME_RE`）而不是穷举字典，因为分区名有上百个且会变。
2. 否则用**细分规则表**匹配标题，命中即给该组 +2 分（细分类别的判别力比零散特征词强）。
3. 再叠加零散特征：死伤/金额/百分比等数字型事件特征 → 热点；
   第一人称、口语化语气词、短感叹 → 梗。
4. 仍打平时按**标题形态**兜底（短句偏梗，长叙述偏热点）。

> 这是**规则法，不是模型**，必然存在错判的个例。所以每条都带一个「依据」（`via`），
> 展开话题后可以看到它为什么被分到这一组。规则表集中在 `lib/classify.js` 顶部，改起来很直接。

### 话题聚合（决定「综合热度」有没有意义）
同一件事常常同时占着好几个榜位。聚类的目标是**认出这些是同一条**。

用**共享的、有区分度的词**作为信号（「郑钦文」「桂花香」「复联5」），
而不是长字面重合 —— 同义改写几乎没有 5 字以上的公共子串，但都含同一个实体。做法：

1. 候选词只取 **3–6 字纯中文 n-gram**，且**至少被 3 条命中**。
   2 字 gram 会产生大量偶然重合（`广州把健身房搬进地铁` 与 `宋雨琦广州演唱会` 共享「广州」；
   `新人第1次编曲` 与 `北方人第一次闻桂花香` 共享「人第」）；只出现 2 次的 3 字片段
   多半是 `请查收`、`拍到了` 这类**句式片段**，同样不能用。
   另外再挡一层：以功能字收尾（了/的/到/么…）或以人称词开头的一律丢弃。
2. **每条只认一个「主词」，不做传递闭包。** 早期版本让任意共享词的条目两两合并，
   结果是 A—词1—B—词2—C 一路串下去，把十几条互不相关的视频粘成一大坨。
   改成按键分组后簇与簇天然不相交，链式误并直接消失。
   主词的挑法是**先看文档频次（越高越可能是话题本体），频次相同再取更长的**——
   反过来优先长词会选中 `武汉网球` 这类只出现两次的碎片，反而拆散了同一件事。
3. 再补一轮**长字面重合**（最长公共子串 ≥ 6），兜住近似重复标题，
   以及 `复联5定档…全球领先上映` 这类靠中文 gram 抓不到数字后缀的情况。

### 综合热度（只用于热点榜）
```
综合热度 = 该话题下所有条目的热度之和
```

⚠️ **B站热度是播放量、抖音是热度值，两者量纲不同**，求和是「并排叠加」而非严格可比。
面板同时显示**条目数**与**平台构成**，便于判断某个名次是「一条极高」还是「多条中等」堆出来的。
**流传榜刻意不用这个指标**，见下。

### 流传度（流传榜用）

```
流传度分 = 使用条目数 + 2 × (出现天数 − 1) + 3 × (平台数 − 1)
```

- **使用条目数**（主要因子）：今天有多少条**不同的**热搜词/热榜条目用到了这个词；
- **出现天数**：跨天持续出现才算「反复用」，而不是一次性热搜；
- **平台数**：B站与抖音都出现，说明跨平台扩散。

⚠️ 拿不到「真实用户数」，所以用「不同榜单条目数」当代理。一条热榜条目背后可能是成千上万人在用
同一个词，这个代理**偏保守但方向正确**——它衡量的正是「被多少人反复用」。

**梗词是怎么抽出来的**：当天短语条目两两求 **极大公共子串**（`commonSubstrings`），
而不是滑窗 n-gram。原因是后者会把 `全球领先上映` 碎成十几个错位片段
（`球领先上` / `领先上映` / `全球领先` …）直接霸占整个榜单；极大公共子串直接给出完整那一段。
历史各天也做同样的提取，好让「今天只出现一次、但连着出现好几天」的老梗也能进榜（`days ≥ 2`）。

**入选与过滤**（每一步都对应一个真实踩过的坑）：

| 规则 | 挡掉的东西 |
|---|---|
| 必须今天还在用 | 已经退潮的词 |
| 今天被复用 ≥2 次，或跨天 ≥2 天 | 一次性热搜 |
| 2 字纯中文片段要求 ≥3 次 | `广州`、`联盟`、`B站` 这类偶然重合 |
| 含数字时，被数字切开的每段都要 ≥2 字 | `下24分`（`下`/`分` 都是单字残片）；而 `复联5定档` 两段都成词，放行 |
| 混着中文却以数字收尾/开头 | `定档1` —— 公共子串蹭到「定档」后面恰好都是 1 |
| 功能字收尾 / 功能字或人称词开头 | `拍到了`、`来到了`、`次中国行`、`第一次`、`有多` |
| 泛用词表（国家名、平台名、身份词、句式模板） | `中国`、`网友`、`B站`、`请查收` |
| **领域类别词本身**（演唱会/比赛/电影…） | 两位不同歌手的「演唱会」不该算同一个梗 |

> 最后一条的判定表**刻意剔除了「网络流行语」那条规则**：那条规则里列的就是梗本身
> （破防 / 整活 / 上头 / 绝了 …），如果拿全表去排除，会把真正的梗一起排掉。
> 见 `DOMAIN_CATEGORY_RES`。

### 其他指标
- **持续热梗**：对每天的热搜关键词做「跨天出现的天数」计数，取 ≥2 天者。
- **跨平台共现**：把两侧短语切成 3–4 字 n-gram，取同时命中 B站与抖音的词；
  纯数字丢弃，并用「最长公共子串 ≥ 长度−1」判重去掉滑窗错位的近义词。
- **标题高频词**：3–4 字 n-gram 词频，出现 ≥3 次并过滤功能词。
  这是**中文无分词器时的启发式**，只作参考。

## 定时与数据

- **刷新时刻**：每天 `06:00` 本地时间（`lib/index.js` 里的 `REFRESH_HOUR` 常量，改成 0–23 即可）。
- **启动补抓**：插件激活时如果当天目标时刻之后还没有快照，会立刻在后台补一次，
  不阻塞插件加载。
- **手动刷新**：面板右上角「立即刷新」按钮，走 `refresh` endpoint，抓完立刻回填页面。
- **打开页面时的轮询**：每 5 分钟拉一次 `feed`（只读 Host 缓存，不触发抓取）。
- **数据落盘**：`$DSH_HOME/storages/dsh-hotspot/history.json`
  （Windows 上默认是 `%USERPROFILE%\.dsh\storages\dsh-hotspot\history.json`），保留最近 30 天，
  写入采用「先写 `.tmp` 再改名」，进程中途退出不会留下半个 JSON。

## 线上协议（Host ⇄ Client）

客户端调用：

```js
ctx.connection.rpc.call('/dsh-hotspot', 'feed' | 'status' | 'refresh', payload)
```

Host 侧**不能**直接用 `ctx.connection.rpc.handle()`：该 API 内部取到的是 Connection 服务
自己的 context（其 `inject` 只有 `credentials`，没有 `webServer`），在当前 DSH 版本上会抛

```
Error: cannot get property "webServer" without inject
```

因此 `lib/rpc-channel.js` 由插件自己 `inject 'webServer'`，注册一条 prefix 路由，
并逐字段复刻 `dsh-client-connection` 的 `/api` 传输语义（信封校验、端点匹配、
`server-response` 编码、信任栅栏、`node:http ⇄ fetch` 桥接）。客户端侧完全不用改。

信任栅栏优先走 `ctx.connection.requestRejection(req)`（Host/Origin 校验 + 浏览器会话 Cookie
认证），不可用时退回「仅 loopback」兜底。注意 `requestRejection` 必须以**方法形式**调用，
抽成裸函数会因丢失 `this` 而恒判 403。

## 开发与迭代

- **客户端半边（`client/client.js`）**：DSH 的 `client-hmr` 默认每 500ms stat 轮询一次各插件
  的客户端产物，文件一变就发布新 rev 并推给浏览器，**改完直接生效，不用重启、不用刷新页面**。
- **Host 半边（`lib/*.js`）**：**已为本插件打开源码监听**，改完也会自动重载，不用重启宿主进程。
  配置写在 profile patch（`~/.dsh/profiles/desktop/cordis.patch.yml`）末尾：

  ```yaml
  - id: hmr
    name: "@deepseek-ai/dsh-hmr"
    config:
      root:
        - "/absolute/path/to/wherever/you/cloned/dsh-hotspot"
  ```

  原理：`dsh-hmr` 用 chokidar 监听该目录；文件一变就进入 `partialReload()`，
  清掉 Node 的 ESM `loadCache` 条目并重新 `import()` 插件入口，
  连带其依赖（`stats.js` / `classify.js` / `text.js` …）一起重新解析。
  已实测验证：改动生效、宿主进程 PID 不变（不是重启）。
  想关掉这段监听，把上面那个 `- id: hmr` 条目删掉即可。

  > 若哪天热重载失效，退路仍然是彻底重启：注意「关掉窗口」通常只是收进托盘、
  > 宿主进程仍在跑，要先从托盘菜单退出（或结束所有 `DeepSeek Harness` 进程）。

### 客户端两个容易回归的点

1. **滚动容器必须成链**：`.dh-root` 是 `height:100%` + `display:flex` + `overflow:hidden`，
   真正滚动的是里面的 `.dh-scroll`（`flex:1` + `min-height:0` + `overflow-y:auto`）。
   只给外层加 padding 而没有滚动层，内容会被父容器裁掉、整页无法滚动。
   `client-check.mjs` 每个页签都会断言这两个 class 存在。
2. **样式表必须重写而不是「已存在就跳过」**：热重载时 `<style>` 元素还在，
   若 `installStyles()` 直接 return，CSS 改动永远不会生效（JS 换了、样式还是旧的）。
   所以每次激活都 `element.textContent = CSS`。

### 跑测试

```bash
node tools/smoke.mjs          # Host：真实抓取 + 线上协议 + 落盘 + 统计 + 分类聚合 + 流传度（55 项断言）
node tools/smoke.mjs --real   # 同上，但写入真实数据目录，给插件预热一份缓存
node tools/client-check.mjs   # Client：模块契约 + 五个页签 × 有/无数据 全渲染 + 滚动结构（69 项）
```

两个脚本都不依赖 DSH 运行时，用最小 ctx / React 桩把真实代码路径跑一遍。
`smoke.mjs` 里还包含针对**已修 bug 的回归断言**：

- 只共享 2 字词（`广州`）、句式片段（`请查收`、`拍到了`、`有多`）的标题**不会**被聚成一个话题；
- **视频条目不参与流传榜**；
- 跨天持续但今天只出现一次的梗**能**进流传榜，且 `days` 统计正确；
- `定档1` 这类数字碎片、`演唱会` 这类领域类别词**不会**被当成梗词。

### 写 Host 半边代码时最容易踩的坑

`tools/smoke.mjs` 里的 ctx 桩是**严格**的：它像真实 Cordis 一样，读取一个没有 `inject`
的服务会直接抛 `cannot get property "<name>" without inject`。

这一点很要紧，因为 DSH 里有一类「mixin 访问器」的坑：

```js
// ✗ 抛错：读取 ctx.timeout 本身就会去解析 ctx.timer，
//   而插件没有 inject 'timer' —— typeof 判断挡不住，异常抛在读取阶段
if (typeof ctx.timeout === 'function') { ctx.timeout(fn, ms) }

// ✓ 本插件的做法：不用 timer 服务，原生 setTimeout + effect 清理
const handle = setTimeout(fn, ms);
return () => clearTimeout(handle);
```

所有从 `ctx` 上读服务的地方，都要确保该服务出现在 `lib/index.js` 的 `inject` 数组里，
或者改用 `ctx.get(name)` 做可选读取。桩会在本地就把这类问题拦下来。

## 已知限制

- **流传度用「不同榜单条目数」当代理**：拿不到真实用户数，所以一个词背后到底是
  十个人还是十万人在用，无法区分。代理偏保守但方向正确。
- **流传榜第一天的词条偏少**：流传度要靠「复用」和「跨天」，而单日榜单里真正被
  反复复用的词本来就不多（实测约 9 个）。等 06:00 累积几天后，`出现天数` 这一项
  开始起作用，榜单会明显变长——这也是为什么面板上会显示「统计 N 天」。
- **流传榜覆盖全部短语，不只梗类**：流传度是**短语的属性**，只收梗组会把复用度最高的词
  （如被 6 条同时引用的 `郑钦文`）丢掉。所以两组都收，面板上用 `全部 / 仅梗 / 仅热点`
  让你自己选。若你希望它严格只统计梗类，把 `lib/classify.js` 里
  `memeEntriesOf()` 加一句分组判断即可。
- **梗 / 热点分类是规则法**：不是模型，必然有错判的个例（尤其是既不像新闻、
  也不像娱乐的生活流内容）。每条的判定依据都随展开可见，规则表在
  `lib/classify.js` 顶部，改起来是直接改正则。
- **话题聚合宁可漏、不可错**：策略偏保守，只认「共享有区分度的词」。
  因此同一件事若被改写得完全没有共同实体（例如一条说事件、一条只评论观点），
  仍会各自成簇。这比把不相关的东西并成一大坨要好。
- **综合热度不可跨平台严格比较**：B站是播放量、抖音是热度值，量纲不同，
  求和只是并排叠加。名次请结合「条目数」与「平台构成」一起看。
- **单日快照的统计口径**：「持续热梗」与「趋势图」需要多天数据才有意义，
  插件刚装上的第一天这两处会显示引导文案，第二天 06:00 之后开始有内容。
- **抖音「热 / 新」标签**来自接口的 `label` 字段（1→热，3→新），是尽力而为的映射。
- **客户端与 Host 的时间以本机为准**，不处理跨时区。
- 首帧渲染依赖一次 RPC 往返；Host 缓存为空且当天还没抓完时会先显示「正在加载热点数据…」。
